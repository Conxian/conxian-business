**A backend support connection is not established by the available evidence.** Zoho CRM organization/module and Accounts/Contacts/Deals field metadata reads succeeded through the connected application. Zoho CRM sales metadata and Zoho Desk support are different contracts. Do not substitute sales Tasks/Deals for a ticket lifecycle, infer a Desk tenant from the CRM organization, copy app-connection tokens into a backend, or treat a sale as payment, entitlement or an SLA agreement. No customer record was read and no customer record, module, workflow, message or subscription was changed during this review.

The preferred bounded path is an operations-owned support adapter with a separate provider contract, retaining the Business customer-lifecycle owner (#1424) and operations owner (#1423). Keep Gateway as a compliance pass-through and Nexus as protocol observation; customer ticket bodies do not belong in those proof paths. Select the actual available support product before adding runtime routes:

1. **R0 — provider identity:** verify the actual support tenant, region, organization/department and supported API through scoped metadata; record the accountable service owner and authoritative support policy in restricted records. A CRM module flag is not support API authorization.
2. **R1 — adapter:** configure a backend-specific, least-privilege OAuth identity through existing secret provisioning. Start with read-only provider/organization validation and explicit unavailable states. Bound timeouts/response sizes, reject redirects that could forward credentials, and never log tokens or provider bodies. No customer-facing capability flag until the adapter is wired into the deployed backend.
3. **R1/R3 — lifecycle:** reconcile stable application tenant/customer and provider IDs through a restricted mapping. Define allowed fields, retention/deletion, redaction, durable event IDs, retry/outbox behavior and duplicate/out-of-order handling before enabling ticket writes. Separate human support requests from engineering GitHub issues; GitHub remains the sole engineering work tracker.
4. **R3 — evidence:** test wrong tenant/department, revoked or expired token, insufficient scope, malformed/partial responses, pagination, rate limits, timeout, outage/recovery, replay and restart. Verify each permitted operation against the intended deployment; organization discovery alone is not ticket lifecycle acceptance.
5. **R4/R5:** independently accept the exact artifact, provider boundary and support scope before advertising availability or response commitments. Retain service packaging review dimensions and accepted-exit timing for economics #1419 and whitepaper #1422.

## Research findings that change implementation choices

- **Native dependency compatibility:** the actual failing Wallet CI reports sha2 0.11.1 requires Rust 1.88, while both native crates declare Rust 1.85 and their CI uses 1.85.1. The [upstream changelog](https://github.com/RustCrypto/hashes/blob/master/sha2/CHANGELOG.md) records the minimum-version change and an AArch64 backend correction. Preserve that improvement; evaluate a coordinated compatibility migration instead of suppressing MSRV checks or discarding the update without review.
- **Taproot Assets:** use the actual [VerifyProof](https://lightning.engineering/api-docs/api/taproot-assets/taproot-assets/verify-proof/) and [ownership verification](https://lightning.engineering/api-docs/api/taproot-assets/asset-wallet/verify-asset-ownership/) contracts, with the [protocol proof format](https://docs.lightning.engineering/the-lightning-network/taproot-assets/taproot-assets-protocol), when evaluating the preserved prototype. Local object transitions and digest formatting are not provider verification or Bitcoin state acceptance.
- **Babylon:** compare prototype transitions against [staking transaction/script requirements](https://docs.babylonlabs.io/guides/overview/babylon_genesis/specifications/bitcoin_staking_scripts/) and actual [query interfaces](https://docs.babylonlabs.io/operators/babylon_node/babylon_cli/query/). Provider/network identity, observed confirmations, delegation state and reward evidence must be independently obtained before production claims.
- **Source coverage:** [GitHub CLI pagination](https://cli.github.com/manual/gh_api) explicitly distinguishes each page and supports an outer array with `--slurp`. Use that boundary and authenticated visibility, not a dependency inventory or a fixed result cap, for the scanner. Separately enumerate open PRs/checks and reconcile immutable heads before merging.
