## Recommendation

Concentrate implementation on a recoverable, authenticated service baseline,
operation-level capability evidence and real payment/entitlement journeys.
Qualify decentralised providers against that baseline rather than building a
parallel platform or migrating critical state prematurely. Keep one coherent
implementation item per repository and finish its release/operation follow-through
before optional expansion.

Keep research, public protocol interoperability, managed services, hardware custody
and restricted business records as explicit boundaries. The wider ecosystem can
contribute maintained adapters, test vectors and independent operation without
obtaining private credentials, customer/deal data or revenue rights.

## Material contradictions and dispositions

1. **Nexus ownership:** the old whitepaper says execution layer; current Nexus
   discovery says observation/verification and assigns execution to Gateway.
   The new evidence draft follows the owning runtime boundary.
2. **Mainnet and own protocol:** legacy ALEX/ConxianCSF launch wording conflicts
   with the accepted network-agnostic pivot. Existing external-network liveness
   does not mean Conxian's adapters are deployed or accepted.
3. **Hardware and thresholds:** blanket Stable/StrongBox/FROST labels exceed the
   current provider/release evidence. Keep algorithms, device integration,
   ceremony, independent operator control and value-operation support separate.
4. **R5 ambiguity:** the preserved machine phase catalogue defines deferred
   research/experiments, while some later prose uses R5 for sprint exit.
   This overlay keeps R5's original meaning. Accepted exit is an R4 decision;
   publication/economics follow that decision and the relevant owner acceptance.
5. **ITIL terminology:** the eight activities are Discover, Design, Acquire,
   Build, Transition, Operate, Deliver and Support. R0–R5 are internal work
   groups; the classic five-stage lifecycle is not represented as ITIL 5.
6. **Autonomy and review:** the old factory Tier 0 “no guardrail”/automatic
   merge-and-deploy proposal cannot supersede current review or release rules.
   Safe automation prepares reviewable changes and gathers evidence.
7. **Economics:** historical “O(1)” costs, guaranteed uptime/yield, valuations,
   percentage splits and competitor snapshots require actual current evidence
   and governing decisions; none is activated by this review.
8. **Whitepaper state:** prepare and correct the draft now. Final authoritative
   publication stays under #1422's accepted-sprint-exit prerequisite. A merged
   source/document PR alone cannot satisfy it.

## Capability-based implementation order

The [roadmap](../architecture/ROADMAP_12_MONTH_CONTROL_PLANE.md) replaces the old
calendar as the current planning view while preserving its historical copy.

- **R0, continuous:** reconcile source, research, issue ownership, claims, rights
  and actual service obligations. This snapshot and its validator provide a
  concrete, reviewable update.
- **R1, executable now:** finish real runtime contracts and consumer pagination;
  preserve transactional writes, immutable promotion/dependency checks and
  operator-facing errors. Validate negative cases and supported journeys.
- **R2, operation-specific:** qualify provider identity, collateral, actual
  hardware and replay for value operations; independently administer the public
  artifact/backup/compute pilot appropriate to each workload.
- **R3, integration:** deploy the accepted artifact in the correct isolated lane,
  prove authenticated journeys and actual state recovery, then real billing and
  entitlement with measured costs and support behavior.
- **R4, acceptance:** bind all relevant results to the exact artifact, environment,
  accountable owner and independent review. Preserve rollback and customer
  continuity before changing primary providers.
- **R5, research lane:** timebox MeshLLM, BitVM3, alternative state systems,
  delegated agent execution and M&A hypotheses. Admit only bounded pilots that
  satisfy their existing prerequisites. Stop or revise when evidence fails.

R1 and appropriate R2 work can run independently where their contracts allow it.
Hardware signing qualification is not a prerequisite to publishing already
approved public documentation; public IPFS success cannot authorize signing.

| Engineering continuity | GitHub remains canonical; qualify export/mirror recovery as an additional path | A mirror becomes an unreviewed competing issue/release authority |

No candidate is a universal cure for packaging, missing runtime contracts, legal
rights, real-device qualification, independent approval or absent customer demand.
