#### Executable Render source read-back

The existing `scripts/verify_render_deploys.py` has an explicit `--expected-deployments` mode. Supply a release-specific manifest from restricted operational records, with schema version 1 and a nonempty `deployments` array. Each entry has exactly `service_id`, `repository` (`Conxian/name`) and `commit` (full 40-character lowercase Git SHA). Service IDs are unique and the entries must cover every repository in `--scope`; multiple intended services for one repository can be listed. Use a bounded scope for the actual approved lane, rather than editing the default intended-runtime scope just to hide missing services. Select intended services explicitly: a static site cannot stand in for the control-plane service even if it has the same repository/SHA.

```bash
python3 scripts/verify_render_deploys.py --owner-id "$RENDER_OWNER_ID" \
  --scope /restricted/approved-lane-scope.json \
  --expected-deployments /restricted/accepted-release.json --summary-only
```

Credentials come from the process environment, never manifest content. Invalid/partial manifests fail before provider access. The ordinary metadata audit remains available without this argument, but reports `expected_source_checks_passed: null`; it provides no source-binding result. Release mode requires exact service/repository/SHA and live status. Other scoped audit failures still fail the command. `metadata_checks_passed` and `expected_source_checks_passed` remain distinct, and `runtime_or_release_authority` is always false. Detailed output and actual manifests stay restricted; `--summary-only` emits booleans/counts only. This is one read-only provider snapshot, not continuous assurance or a substitute for final post-transition read-back, workload tests, configuration identity, image provenance or independent acceptance. No deploy or provider configuration change is performed by this command.

Research checked against current primary Render documentation: [deploy lifecycle and exact commits](https://render.com/docs/deploys), [health-check semantics](https://render.com/docs/health-checks). A successful deploy request is asynchronous; older workloads can remain after a failed rollout. HTTP health checks can accept redirects, so an auth redirect is not an authenticated-journey test. A restart uses the running deployment's configuration and cannot establish that newly saved environment changes were applied. Fresh provider inventory and deployment read-back remain restricted evidence, not public infrastructure listings.
